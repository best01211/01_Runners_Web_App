# 배포 준비 점검 — 2026-10-12

이 문서는 수정 전 진단이다. 후속 코드 수정과 검증 결과는 [제품 안정화 변경](product-stabilization-2026-10-12.md)에 기록했다.

범위: 위치 추적 제외. 인증, 회원 관리, 일정 게시글, 참가, 출석, 댓글, 랭킹, 운영 설정.

판정: 현재 상태에서 일반 회원 대상 운영 배포는 보류한다. 기능 골격은 상당 부분 구현됐으나 권한 우회, 출석번호 노출, 정기런 신청 흐름 단절이 있다. 기존 테스트 통과를 운영 준비 완료로 판단할 수 없다.

## 확인 방법과 한계

- 저장소의 화면, API, 003~008 SQL과 테스트를 읽었다. 운영 Supabase의 데이터와 설정은 조회하거나 변경하지 않았다.
- 앞선 동일 세션의 인증 5개, 출시 로직 7개, 출시 DB 32개 검증은 통과했다. 추적 테스트 결과는 이번 배포 판정에서 제외한다.
- 추가 로컬 PostgreSQL 재현에서 정지된 일반 회원의 가입 승인 RPC 호출이 성공했다.
- UTC/Asia/Seoul 환경의 같은 datetime-local 문자열 변환 결과가 9시간 다른 것을 확인했다.
- ESLint/TypeScript 재검사는 실행이 장시간 완료되지 않아 통과 판정을 내리지 않았다. 프로덕션 빌드 역시 앞선 점검에서 완료되지 않았다.
- 기본 profiles/schedules/참가 테이블의 초기 스키마가 저장소에 없다. 운영 DB에 별도 트리거나 RLS 정책이 있을 가능성이 있어 해당 항목은 별도로 확인해야 한다.

| 회원 승인/역할/상태/탈퇴 | 화면·API·일부 RPC 있음 | 권한과 상태 전환 보완 필수 |

| 독립 공지/자유 게시판 | 화면·API·테이블 없음 | 일정 게시글과 별개이며, 출시 요구사항이면 추가 구현 필요 |

| 댓글 | 작성·삭제·공지 작성 화면 있음 | 삭제 본문 노출 수정; 대댓글 작성·수정 UI 없음 |

| 운영 설정 | 점수·서비스 상태 저장 있음 | 예약 점검과 일부 제한은 별도 동작 없음 |

## 배포 전 필수 수정

### P0: 가입 승인 RPC 권한 우회 — 로컬 재현 완료

위치: `supabase/migrations/003_member_approval.sql`, `review_pending_member`.

활성·승인된 프로필만 SELECT한 후 `actor_role not in ('staff','admin')`으로 차단한다. 정지/제한 계정은 SELECT 결과가 없으므로 actor_role이 NULL이고 IF 조건도 NULL이 되어 차단되지 않는다. authenticated에 실행 권한이 있으므로 직접 RPC 호출을 고려해야 한다. 정지된 일반 회원이 대기 회원을 approved로 변경하는 것을 실제 함수로 재현했다.

수정: actor_role IS NULL을 명시적으로 거절하거나 EXISTS 기반의 긍정 권한 검사로 변경한다. 제한·정지·탈퇴·프로필 없음·대기 계정의 직접 호출 거절을 회귀 검증한다. API만 수정해서는 해결되지 않는다.

### P0: 일정 상세 API에서 출석번호 노출

위치: `src/app/api/schedules/[scheduleId]/route.ts:14`.

로그인 회원에게 schedules 전체 열을 반환하므로 attendance_code도 포함된다. 출석 전용 API가 운영자에게만 번호를 제공하더라도 다른 조회 경로로 노출된다. 원격 회원이 번호를 가져가 인증할 수 있는 구조다.

수정: 조회 응답 열을 명시적으로 제한하고 모든 일정 응답과 직접 DB 조회 권한을 점검한다. 일반 회원 응답에는 attendance_code가 없어야 한다.

### P1: 삭제 댓글의 본문이 API에 남음

위치: `src/app/api/schedules/[scheduleId]/comments/route.ts:3`.

삭제 표시만 저장하고 목록 API는 전체 본문을 그대로 반환한다. 화면의 '삭제된 댓글' 표시는 데이터 비공개 처리가 아니다.

수정: 삭제된 댓글의 content 등 비공개 필드를 응답에서 제거하거나 자리 표시 응답으로 변환한다. 직접 Supabase SELECT도 같은 정책인지 확인한다.

### P1: 정기런 참가 흐름이 화면에서 막힘

위치: `src/components/participation/participation-panel.tsx:13`.

정기런은 그룹이 없으면 참가 버튼을 비활성화한다. 그룹 생성 폼은 번개런에만 표시된다. 일정 생성도 그룹을 생성하지 않는다. 새 정기런을 만들고 일반 화면에서 참가까지 진행할 수 없다. 그룹 생성 API는 있으므로 운영진 UI를 연결하면 된다. 정기런 그룹 필수 정책은 RPC에서도 강제해야 한다.

### P1: 참가 신청과 그룹 배정이 분리됨

위치: `src/app/api/schedules/[scheduleId]/participation/route.ts:44`.

신청 RPC 이후 그룹을 별도 UPDATE하고 오류를 무시한다. 요청한 그룹을 성공 응답에 넣으므로 실제 저장과 응답이 다를 수 있다. POST에는 그룹이 해당 일정 소속인지 검사도 없다. 그룹 변경 PATCH 역시 출석 상태 조회와 쓰기가 분리되어 동시 요청에 취약하다.

수정: 신청·그룹 검증·배정을 같은 RPC 트랜잭션으로 처리하고, 그룹 변경도 일정 잠금 아래 실행한다. 번개런 생성자의 자동 참가 등록 오류도 처리한다.

### P1: 출석 이후 참가 취소 차단이 불완전함

위치: `supabase/migrations/004_participation_helpers.sql:83`, `008_release_fixes.sql`의 open 분기.

취소 RPC는 participation_locked와 마감 시각만 확인한다. 출석 시작 RPC는 해당 잠금을 설정하지 않고 취소 RPC도 attendance_opened_at을 확인하지 않는다. 저장소 SQL만으로는 출석 시작 후 취소를 확실히 막지 못한다. 출석 기록과 참가 상태가 달라질 수 있다. 초기 DB의 별도 트리거 존재 여부는 미확인이다.

수정: 출석 시작·취소가 같은 일정 행을 잠그도록 하고 시작 후 취소를 DB에서 거절한다. 종료 후 미확인으로 수동 변경하는 정책도 정해야 한다. 회원 화면에 본인 출석·지각·불참 결과를 표시한다.

### P1: 일정 시간의 서버 시간대 의존

위치: `src/components/schedules/schedule-form.tsx:6`, `src/lib/validation/schedule.ts`.

datetime-local을 시간대 없는 문자열로 전송하고 서버가 Date.parse/new Date로 해석한다. UTC 서버에서는 서울 19:00 입력이 UTC 19:00으로 저장될 수 있다. 서울에서 의도한 UTC 10:00과 9시간 차이를 재현했다.

수정: 한국 시간 입력 정책을 명확히 하고 UTC ISO 또는 오프셋 포함 값을 전송·검증한다. 목록·상세 표시도 Asia/Seoul로 통일한다.

### P1: 계정 상태 변경이 탈퇴 처리와 충돌

위치: `src/components/admin/member-actions.tsx`, `src/app/api/admin/members/[userId]/route.ts`.

관리자 상태 선택에서 withdrawn을 직접 저장할 수 있으나 실제 탈퇴 RPC의 익명화와 Auth 삭제를 수행하지 않는다. 탈퇴 대기 계정의 수동 활성화도 가능하다. staff는 rankingExcluded만 보내면 대상 역할 제한 없이 처리할 수 있다. 역할·상태·대상의 권한 범위를 일관되게 정해야 한다.

수정: withdrawn 전환은 전용 탈퇴 흐름으로만 허용한다. 대기 신청과 상태를 함께 검사하고 허용 전환을 검증한다. 관리자 변경 이력을 보존한다.

### P1: 비공개 시즌 조회 우회 및 기본 시즌 갱신 실패

위치: `src/app/api/admin/seasons/route.ts`.

GET은 로그인만 확인하고 service-role로 전체 시즌을 반환하므로 비공개·숨김 시즌도 일반 회원이 조회할 수 있다. POST는 기존 기본 시즌을 해제한 후 새 시즌을 별도로 생성하므로 생성 실패 시 기본 시즌이 사라진다.

수정: GET 권한/공개 필터를 적용하고 기본 시즌 변경을 트랜잭션으로 처리한다.

## 출시 범위에 맞춰 보완할 기능

- '게시글'이 일정 공고를 뜻하면 CRUD가 있다. 독립 공지·자유게시판을 뜻하면 미구현이다.
- 대댓글 작성, 댓글 수정, 기존 댓글 공지 전환은 화면에 없다. API 존재만으로 사용자 기능 완료라고 할 수 없다.
- 회원 승인 거절 사유·재신청 허용 값은 기록하지만 회원이 사유를 확인하고 재신청하는 흐름은 없다.
- 운영진 정원 포함 설정은 저장하지만 참가 RPC와 인원 계산은 모든 참가자를 센다.
- 페이서 가산점은 계산하지만 페이서 지정 화면/API는 없다.
- 시즌은 생성만 가능하고 수정·기본 전환·공개 전환 화면/API가 없다.
- 로그인 화면에는 회원가입 링크와 가입 완료/이메일 확인 안내가 없다. callback의 인증 실패도 안내하지 않는다.
- 일정 대표/코스 이미지 입력·저장은 있지만 상세 화면에 표시하지 않는다.
- 점검 시각은 저장하지만 자동 시작/종료는 없다. restricted도 일반 회원 전면 접근 제한으로 처리된다.
- 목록 페이지네이션, 통신 실패 안내, 중복 클릭 방지, 운영 오류 기록을 보완한다. 회원/댓글/일정 목록은 응답 건수 제한 영향을 받는 조회다.
- 로그인 next 이동값을 내부 경로로 제한하고, 쓰기 API의 Origin·활성 승인 계정 검사 및 입력 오류 처리를 통일한다.

## 진행 순서와 완료 기준

1. P0 두 건 수정: 직접 RPC 권한 거절, 모든 일반 회원 응답에서 출석번호 제외. 삭제 댓글·비공개 시즌 노출도 함께 수정한다.
2. 참가/출석 DB 처리 통합: 정원·그룹·출석 이후 취소·동시성 검증. 시간대 저장 수정.
3. 회원 상태 전환과 핵심 UI 연결: 전용 탈퇴, 정기런 그룹 관리, 회원 출석 결과, 가입 안내. 게시판 범위를 확정한다.
4. 랭킹/운영 정책 완성: 페이서·정원 계산·기본 시즌·필요한 시즌 변경. 출시에서 제외할 기능은 입력 UI와 안내도 조정한다.
5. 별도 검증 환경에서 실제 Supabase Auth·RLS·메일·Storage를 확인하고 모바일 사용자 흐름을 실행한다.
6. ESLint·TypeScript·프로덕션 빌드 및 핵심 E2E 통과 후 소수 회원 대상으로 제한 공개한다. DB 백업·마이그레이션 절차·이전 앱 복귀 절차·오류 확인 방법을 준비한다.

핵심 E2E: 가입→메일 확인→승인→로그인→정기런/번개런 생성→그룹 등록→참가→출석 시작→인증→지각 수정→종료→랭킹 반영. 댓글 작성/삭제 응답, 정지 계정의 직접 RPC 거절, 탈퇴 반려/재신청/승인/삭제 재시도, UTC 서버의 한국 시간 저장도 포함한다.

이번 작업은 진단이다. 제품 코드와 운영 DB는 변경하지 않았다. 로컬 권한 재현 스크립트는 Git 제외 경로 `.test-output/deployment-approval-audit.mjs`에 저장했다.
