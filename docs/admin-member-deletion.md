# 관리자 사용자 삭제

## 적용

010 적용 후 `supabase/migrations/011_admin_member_deletion.sql` 전체를 Supabase SQL Editor에서 실행한다. 이 SQL은 테이블·함수·권한만 준비하고 기존 회원이나 기록을 삭제하지 않는다. 재실행 가능하다.

관리자 → 회원 관리 → **사용자 정보·기록 삭제**에서 삭제 범위를 확인하고 대상 회원 아이디를 입력한 뒤 **영구 삭제 실행**을 누른다. 승인 대기·거절·정지·제한·탈퇴 계정 및 일반 회원·운영진 계정에 사용할 수 있다. 본인과 관리자 역할의 계정은 보호한다.

## 삭제 범위

- 대상의 개인정보와 profiles 행, 가입 승인 기록, 참가 기록, 출석 기록, 작성 댓글, 개인 대회 출전·계측·계측 감사 기록, 탈퇴 요청과 역할 변경 이력을 삭제한다.
- 대상 소유 Storage 객체와 `01runners-images/{사용자 UUID}/` 폴더의 프로필 사진을 Storage API로 삭제한다.
- Auth Admin API의 하드 삭제로 인증 계정을 삭제한다. 정상 완료하면 동일한 아이디·이메일로 새 회원가입을 할 수 있다. 새 가입은 새 UUID와 승인 대기 상태를 가진다.
- 공동 일정·대회·정기런 양식 및 다른 회원의 참가·출석·계측 기록은 유지한다. 필수 작성자/운영자 연결은 처리 관리자에게 이전하고, nullable 운영자 연결은 비운다. 삭제 댓글에 달린 다른 회원의 답글은 부모 연결을 비워 별도 댓글로 유지한다.
- 삭제 실행 이력에는 대상 UUID·처리 관리자 UUID·시각·건수만 남긴다. 완료 시 확인용 아이디와 파일 목록을 제거한다.

공동 일정의 제목·설명 등 공유 콘텐츠는 자동 삭제하지 않는다. 개인정보가 해당 콘텐츠에 직접 입력되어 있다면 관리자가 내용을 따로 수정해야 한다.

## 처리 순서와 실패 대응

1. 서버 API와 DB 함수 모두 활성·승인된 관리자 권한, 본인/관리자 보호, 확인 아이디를 검사한다. DB 함수는 service_role에만 실행을 허용한다.
2. DB 정리는 한 트랜잭션이다. 프로필을 참조하는 소유 기록과 종속 기록을 정리하고 프로필을 삭제한 뒤 작업 이력을 저장한다. 대상 행 잠금과 관리자 삭제 작업 직렬화를 사용한다.
3. Storage를 버킷별로 정리하고 Auth 계정을 삭제한다. 외부 서비스 처리는 DB와 하나의 트랜잭션이 될 수 없다.
4. 외부 삭제에 실패하면 **완료되지 않은 사용자 삭제 → 삭제 계속하기**에서 재시도한다. 이때 DB 정보는 이미 삭제된 상태이며 Auth 계정이 남아 있으면 같은 이메일 재가입이 완료되지 않을 수 있다.
5. 완료된 작업은 반복 요청으로 다시 실행하지 않는다. 동시 재시도에서도 완료 상태를 이전 단계로 되돌리지 않는다.

조회된 운영 스키마의 기존 테이블들과 저장소 테이블들을 지원한다. 알려지지 않은 필수 종속 테이블, 복합 외래키 또는 예상 밖의 회원 참조는 오류로 중단한다. 임의로 다른 회원 데이터를 지우거나 제약조건을 해제하지 않는다. 서버 로그의 `UNSUPPORTED_DELETE_DEPENDENCY` / `UNSUPPORTED_MEMBER_REFERENCE`를 확인해 해당 관계를 추가로 검토해야 한다.

## 검증

`npm run test:member-deletion-db`의 PostgreSQL fixture 검사 39개와 `npm run test:release`의 단위 테스트 29개가 통과했다. 관리자 권한, 본인/관리자 보호, 확인 아이디, Auth 삭제 오류 재현, 소유 데이터 삭제, 다른 회원 데이터 유지, 미지원 의존성의 전체 롤백, Storage 소유권, 재시도와 완료 상태를 검증한다. ESLint·TypeScript·프로덕션 빌드도 통과했다.

운영 DB에 011을 적용하거나 실제 회원을 삭제하지 않았다. SQL 적용 후 먼저 폐기 가능한 테스트 계정으로 실제 Storage·Auth 처리를 확인한다.
