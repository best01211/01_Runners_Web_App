# 출시 전 오류 수정 (2026-10-07)

## 적용 순서

1. 운영 DB를 백업하고, Supabase SQL Editor에서 기존 003~007 적용 여부를 확인한다.
2. `supabase/migrations/008_release_fixes.sql` 전체를 실행한다. 신규 함수·이메일 동기화 트리거·탈퇴 완료 기록을 추가한다. 실패 시 트랜잭션 전체가 취소된다.
3. 수정한 앱을 배포한다. 008을 적용하기 전에는 새 출석·프로필·탈퇴 쓰기 기능을 사용할 수 없다.
4. Supabase Authentication에서 이메일 변경 확인과 Secure email change를 활성화하고 운영 HTTPS 주소 및 `/auth/callback`, `/auth/reset-password`를 허용한다. 인증 이메일 변경은 Supabase Auth가 완료한 뒤에만 profiles에 반영된다.

실제 운영 DB 마이그레이션, 메일 발송 및 사용자 데이터 변경은 이번 로컬 작업에서 실행하지 않았다.

## 수정 내용

- 로그인·비밀번호 변경은 `profiles.email` 대신 사용자 ID로 조회한 실제 Auth 이메일을 사용한다. 과거 이메일 불일치가 있어도 잘못된 이메일로 인증하지 않는다. 내 정보 화면도 현재 Auth 이메일을 표시한다.
- 프로필 저장 시 이메일을 직접 덮어쓰지 않는다. 이메일 변경은 Auth 확인 메일 흐름을 거치고 확인된 변경만 DB 트리거로 동기화한다. 프로필 저장 후 메일 요청 실패 시 부분 완료 내용을 안내한다.
- 일반 회원의 번개런 수정에서 정기런·훈련·이벤트로 유형을 바꾸는 요청을 거절한다.
- 출석 시작·번호 인증·운영자 수정·종료를 DB 함수의 트랜잭션으로 처리한다. 일정 행 잠금으로 동시 요청을 직렬화한다. 이미 처리된 출석 및 운영자가 미확인으로 수정한 기록은 번호 재입력으로 덮어쓰지 않는다. 취소·삭제 일정과 비참가자도 차단한다.
- 탈퇴 신청과 계정 제한, 탈퇴 승인과 프로필·댓글 익명화를 각각 하나의 트랜잭션으로 처리한다. 반려 이력은 보존하며 재신청을 허용한다.
- Auth 계정 삭제는 외부 Auth API이므로 DB 트랜잭션에 포함되지 않는다. 실패하면 익명화와 접근 제한을 유지하고 관리자 화면에 **인증 삭제 재시도**를 제공한다. 승인 RPC는 재시도가 가능하고, 이미 없는 Auth 계정도 완료로 처리한다. 완료 표시 저장 실패도 재시도가 가능하다.
- 랭킹 화면과 통계 API는 같은 계산을 사용한다. 출석·지각·불참 점수, 출석/지각 페이서 가산점, 최소 활동(출석+지각), 게스트 포함 정책을 반영한다. 관리자·비활성·미승인·테스트·랭킹 제외 계정과 취소/삭제 일정을 제외한다.
- 기본 시즌 또는 선택한 시즌의 일정 시작 시각을 한국 시간 기준으로 필터링한다. 시즌 종료일 전체를 포함한다. 기본 시즌이 없으면 전체 기간이라고 안내한다. 일반 회원에게는 비공개·숨김 시즌을 제공하지 않는다.
- 출석과 페이서 조회를 페이지 단위로 수행해 서버 응답 건수 제한으로 랭킹이 누락되는 문제를 방지한다.

## 실제 서비스 확인

- 이메일 변경을 요청하고 확인 전 기존 이메일로 로그인되는지, 확인 후 새 이메일로 로그인·비밀번호 찾기가 가능한지 확인한다. 운영 메일 설정과 실제 발송은 별도 확인해야 한다.
- 회원이 본인 번개런 유형 변경 API를 직접 호출해도 이벤트/정기런 전환이 거절되는지 확인한다.
- 출석 시작 → 번호 인증 → 중복 인증 거절 → 운영자 지각 변경 → 재입력 거절 → 종료를 확인한다.
- 회원 탈퇴 신청·관리자 반려·재신청을 확인한다. 탈퇴 승인은 실제 개인정보를 익명화하므로 전용 테스트 계정으로 확인한다.
- 점수를 변경하고 시즌 경계 날짜·최소 활동·게스트 포함에 따라 랭킹과 `/api/statistics?seasonId=...`가 일치하는지 확인한다.

이메일/랭킹 정책의 의미: 최소 활동은 출석과 지각 합계이며, 불참에는 페이서 점수를 주지 않는다. 별도 시즌 선택이 없으면 공개 기본 시즌을 사용한다.

Auth 삭제는 Supabase의 soft delete를 사용한다. 인증 정보를 삭제하고 익명화된 프로필 ID와 활동 이력의 외래 키를 보존한다. 이미 soft delete된 인증 계정은 재삭제하지 않고 완료 표시를 재저장한다. 실제 Auth API 동작은 전용 테스트 계정으로 확인해야 한다.
