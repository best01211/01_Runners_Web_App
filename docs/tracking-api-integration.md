# 운영진 선수 등록과 MyResult 기록 연동

## 현재 상태와 확인한 근거
- 2026-10-23, 사용자가 제공한 https://myresult.co.kr/176 의 공개 페이지와 해당 페이지의 공개 스크립트를 읽었다.
- 대회 조회 GET https://myresult.co.kr/api/event/176 은 200 JSON을 반환했다. 마스터스 풀코스 코드는 Full, 10km 코드는 10K다. EF(엘리트 풀), EH(엘리트 하프)도 있으므로 같은 거리라는 이유로 자동 연결하지 않는다.
- 페이지가 사용하는 선수 조회 경로는 GET /api/event/{eventId}/player/{bib}다. 대회 176에서 실제 참가자의 배번호 대신 0으로 접근 제한만 검사한 경로(/api/event/176/player/0)와 공개 검색에 나온 과거 기록 페이지의 조회 경로는 모두 401과 {"message":"API key required"}를 반환했다. 인증 우회나 키 추출은 수행하지 않았다.
- 사용자는 키를 아직 발급받지 않았다고 답했다. 따라서 실제 선수 응답을 인증된 상태로 받는 검증은 완료할 수 없다. 웹 스크립트에서 확인한 event_id/course_cd/num/records 및 time_point 필드에 맞춘 어댑터를 구현하고 가상 응답으로 검사했다. 정식 연동 전 제공처 문서와 허가된 선수 응답으로 다시 확인해야 한다.

## 운영진 권한
- 승인된 활성 staff(운영진)는 종목의 회원·배번호·기존 그룹을 지정해 선수 등록/수정이 가능하다.
- 관리자/회장의 기존 관리 권한은 유지한다. 일반 운영진은 코스·그룹·수동 계측·출전 상태·API 설정을 변경할 수 없다.
- 계정 제한·탈퇴 대기·미승인·점검 제한, 다른 종목 중복 등록, 그룹 소속, 정원, 출발 이후/계측 후 기존 선수 변경 잠금을 API와 DB에서 검사한다.
- 운영진의 후보/선수 목록에서 관리자 계정은 숨기고, DB도 운영진이 관리자 계정을 배번호로 등록하지 못하게 한다.

## 주소 입력 위치와 사용 순서
1. 029까지 적용된 DB에 030_tracking_staff_and_timing.sql을 적용한다.
2. 대회 상세 → ‘대회 기록 API 설정’을 연다. 관리 권한이 있는 계정에게만 보인다.
3. https://myresult.co.kr/176 또는 https://myresult.co.kr/api/event/176 을 입력하고 ‘주소 확인 · 종목 불러오기’를 누른다.
4. 풀코스 화면에는 ‘마스터스 풀코스 · Full’, 10K 화면에는 ‘10K’를 선택한다. 주소는 같은 대회의 모든 종목이 공유하고, 종목 코드는 현재 코스에 각각 저장한다.
5. 키가 없어도 주소와 종목 연결을 비활성 상태로 저장할 수 있다. 활성화는 막고 ‘API 인증 설정 필요’를 표시한다. 제공처 장애 시에도 비활성 저장은 외부 조회 없이 가능하다.
6. 제공처에 대회 176의 배번호별 START·구간·FINISH 기록 조회 권한, API 키 발급, 인증 헤더 규격 및 호출 한도를 문의한다. 자동화된 메시지는 보내지 않았다.
7. 발급 후 서버 환경 변수로만 설정한다. 키를 채팅·Git·브라우저·DB에 넣지 않는다.

```dotenv
# 값은 실제 제공처 안내를 따른다. 헤더명을 임의로 가정하지 않는다.
MYRESULT_API_KEY_HEADER=제공처가_지정한_헤더명
MYRESULT_API_KEY_176=제공처가_발급한_값
# 모든 대회에 같은 키를 사용할 경우 MYRESULT_API_KEY를 사용할 수 있다.
```

헤더형 인증을 지원한다. Authorization 방식이라면 값에 Bearer 등 필요한 접두사를 제공처 안내대로 포함한다. 서명/쿼리 등 다른 인증 방식이면 어댑터 보완이 필요하다. 환경 변수 변경 후 Vercel 재배포가 필요하다. 키가 있다는 사실과 키가 실제 유효하다는 사실은 구분한다. 키가 거절되면 ‘API 인증 오류’를 표시하고 재시도를 늦춘다.

8. 주소와 종목을 다시 확인한 후 ‘같은 대회 전체 종목의 자동 수집 사용’을 켠다. 활성화 시 API 대회 날짜·공식 거리·선택 코드를 검증한다. 승인된 실제 응답으로 배번호 한 명부터 검증하고 제공처 호출 한도에 맞춰 운영한다.

## 수집과 예측
- 화면의 기존 DB 조회는 15초마다 진행한다. 외부 수집 트리거는 화면이 보일 때 30초마다 별도 POST를 보낸다. 첫 화면 렌더링은 외부 API를 기다리지 않는다.
- DB lease로 여러 사용자·Vercel 인스턴스가 같은 종목을 동시에 수집하지 않도록 한다. 요청당 최대 40명, 동시 요청 4개, 각 외부 요청 4.5초 제한이다. 40명을 넘으면 커서를 순환하므로 선수별 외부 갱신 간격은 30초보다 길어진다. 제공처 제한 발생 시 5분 대기한다.
- 보는 사람이 없으면 수집하지 않는다. 항상 켜진 스케줄러/cron은 이번에 설정하지 않았다. 다음 접속 때 제공처의 누적 기록을 다시 읽어 따라잡는다.
- event_id, course_cd, num을 확인한 뒤 해당 앱의 entry_id에 연결한다. 숫자 배번호의 앞자리 0은 비교할 때만 정규화하고 저장된 배번호는 보존한다.
- time_point의 HH:mm:ss[.SSS]를 제공처 대회 날짜와 한국 시간대로 결합한다. 미래·출발 이전·미등록 계측소는 제외한다. 날짜를 임의로 추정하거나 잘못된 응답을 실제 위치로 사용하지 않는다.
- 42.20km로 반올림된 도착점은 동일 종목의 마지막 ‘도착/FINISH’ 지점일 때만 공식 42.195km로 맞춘다(차이 50m 이내). 다른 종목/거리/연도는 거절한다.
- 실제 START를 가져오면 해당 출발 시각으로 계산한다. 첫 5km 전 그룹 페이스, 이후 실제 계측 페이스라는 기존 규칙은 유지한다. GPS 위치 수집이 아니다.
- 기록은 source=myresult로 저장한다. 동일 선수·거리 기록은 다시 삽입하지 않으며 기존 수동 기록이나 기존 API 기록을 덮어쓰지 않는다. 제공처가 이미 저장된 기록을 정정하면 별도 확인이 필요하다.
- 지연된 과거 기록을 추가할 수 있으며 앞/뒤 기록의 시간·페이스를 검사한다. 임대 토큰이나 설정 버전이 바뀌면 이전 수집 결과를 반영하지 않는다. 수집된 기록이 있으면 주소/종목 변경을 잠그지만 연동 중지는 허용한다.

## 보안과 파일
- 기존 RLS 정책과 관리자 유지보수 예외는 수정하지 않았다. 선수 등록만 새 권한 함수로 분리했다.
- 조회 주소는 HTTPS myresult.co.kr의 검증된 대회/선수 경로로 제한한다. 사용자 지정 임의 호스트·포트·자격 증명·쿼리·리디렉션은 허용하지 않는다. 원본 응답/개인정보/키는 오류 메시지로 내보내지 않는다.
- 수집 RPC와 lease 테이블은 서버의 service_role 전용이다. 브라우저의 직접 쓰기는 불허한다. API는 매 요청 계정·서비스 접근을 확인하며 새 공유 사용자 캐시는 없다.
- 주요 변경: account-access.ts, tracking-snapshot-server.ts, live-tracking.tsx, timing-source-panel.tsx, live-types.ts/types.ts, myresult.ts, myresult-server.ts, sync-server.ts, /api/tracking/[raceId]/route.ts·source/route.ts·sync/route.ts, 030 마이그레이션.

## 검증 결과
- npm run build, npm run lint 통과(최종 빌드 컴파일 5.9초, 타입 9.5초). 운영 응답 시간 측정값이 아니다.
- 추적 단위 검사 44개, 릴리스 56개, 인증 5개 통과.
- 새 PostgreSQL 검사 27개: 운영진 허용 범위·제한 계정·숨긴 관리자·DB 직접 쓰기 차단·공유 lease·중복·역순 계측·설정 변경 무효화·중지.
- 실제 등록 API 및 수집 조합 검사 20개, API 설정 검사 19개 통과. 키가 없을 때 선수 API를 호출하지 않는 것도 검사했다.
- 스냅샷의 운영진 후보 제공과 관리자 숨김, 기존 등록/삭제 API 검사 통과. 작은 fixture의 선택 코스 읽기는 8회이며 새 source/sync 조회는 기존 독립 조회와 병렬 실행한다.
- 브라우저에서 운영진에게 배번호 등록만 보이는 것, 키 없는 주소·종목 저장, 활성화 차단, 기존 다중 GPX·선수 상세·응원 화면을 검사했다.
- 실제 API 대회 정보 200/선수 기록 인증 필요 401을 확인했다. 인증된 실제 선수 응답, 운영 Supabase/Vercel에서의 수집, 호출 한도·지연·실기기 E2E는 미검증이다. 원격 마이그레이션·배포는 수행하지 않았다.
